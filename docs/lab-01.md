# Звіт до лабораторної роботи №1

**Дисципліна:** Штучний інтелект у програмній інженерії  
**Тема:** «Розробка системи обліку та обробки звернень до технічної підтримки з використанням AI-асистента (Smart HelpDesk)»  
**Назва ЛР1:** «Вимоги та проєктування з AI-асистентом: від неструктурованого запиту до перевірюваної специфікації».  
**Студентка:** Качура Діана • **Група:** ПЗПІ-23-6  
**Дата:** 18 листопада 2026 року.

## 1. Мета роботи

Навчитися використовувати AI-асистента для критичного уточнення вимог, трансформувати неструктурований запит замовника на перевірювану специфікацію та спроєктувати мінімальну архітектуру і REST API системи Smart HelpDesk. Метою є **специфікація**, а не розроблення працюючого програмного продукту: реалізація передбачена у наступних лабораторних роботах.

## 2. Виконана робота

Вихідний приклад Mini Issue Tracker адаптовано до предметної області обліку звернень до технічної підтримки **без розширення обов'язкового обсягу**. Сформовано FR-01–FR-07, майбутню FR-08 (AI-рекомендація), шість вимірюваних NFR, сім user stories для поточного обсягу та одну відкладену user story для ЛР4. Визначено сутності `Issue`, `User`, `Comment`, усі дев'ять поєднань статусів і атомарні правила часткового оновлення. Побудовано компонентну архітектуру з трьох компонентів, ER-модель, дев'ять маршрутів API, два ADR та матрицю простежуваності вимог до майбутніх тестів.

Ключові проєктні документи містяться у `docs/requirements.md`, `docs/architecture.md`, `docs/api-contract.md`, `docs/traceability.csv` і `docs/ai-log.md`.

## 3. Ключові рішення та уточнення

**Рішення 1 — незмінність вихідних правил замовника.** Після створення звернення отримує `OPEN`, типовий пріоритет — `medium`; дозволено призначати двох тестових агентів. CLOSED не може повертатися до попередніх станів і не допускає редагування основних полів, проте коментарі після закриття залишаються дозволеними. Це задані факти методички, а не здогадки AI.

**Рішення 2 — атомарний PATCH.** У контракті явно розділено відсутнє поле (не змінюється), `assignee_id: null` (зняти призначення) і порожній `{}` (422). Запит із одночасно валідною й невалідною зміною відхиляється цілком, а невдале редагування не змінює БД. Це перевіряється за AC-03-02 і `test_patch_atomic_failure_and_closed`.

**Рішення 3 — контрольована AI-інтеграція.** Автоматичне визначення категорії, пріоритету та стислого підсумку залишено на ЛР4. Майбутній AI-модуль видаватиме рекомендацію, а не автоматично змінюватиме звернення; за відсутності LLM основний сервіс працюватиме автономно.

## 4. Використання AI та перевірка результату

Для аналізу було використано ChatGPT (GPT-6). AI допоміг виділити предметні сутності, уточнити граничні випадки та підготувати взаємоузгоджені технічні документи. Під час контролю відповіді перевірено, що чутливі до регістру значення статусів/пріоритетів однакові в user stories, API й матриці станів. Окремо звірено, що 409 застосовується до забороненого переходу, 404 — до відсутнього ресурсу, 422 — до невалідного запиту.

Показовий випадок 1: AI-аналіз допоміг уникнути типового змішування `null` із пропущеним полем у PATCH; перевірка — порівняння вимог §5.5 та прикладу `PATCH /issues/{id}`. Показовий випадок 2: при проєктуванні AI-складової перевірено вимогу, що FR-08 належить ЛР4; тому в поточному контракті немає AI-endpoint і немає автоматичної зміни заявок.

**Журнал:** `docs/ai-log.md`. Технічні уточнення DEC-02, DEC-06 та DEC-07 потребують підтвердження викладача або команди, оскільки вихідні правила не деталізують їх повністю.

## 5. Результати перевірки та простежуваності

Для кожної з семи поточних функціональних вимог FR-01–FR-07 підготовлено принаймні одну user story, позитивний і негативний/граничний критерії, маршрут і майбутній тест. **Покриття специфікації:** `7 / 7 × 100% = 100%`. FR-08 не включено до знаменника, оскільки це майбутня функція ЛР4; цей показник **не є** покриттям коду. Матриця міститься у `docs/traceability.csv`.

Проведено AI-перевірку структури та автоматичну перевірку наявності FR, US, AC, маршрутів і рядків traceability. **Особисте перехресне рев'ю іншого студента ще потребує проведення:** результати слід зафіксувати у `docs/ai-log.md`. Виконання коду, запуск REST API та інтеграційне тестування до ЛР1 не належать.

## 6. Висновки

У ході лабораторної роботи сформовано перевірювану специфікацію Smart HelpDesk, яка розділяє факти замовника, необхідні технічні уточнення та припущення для подальшого погодження. Визначено єдині правила даних, станів і PATCH, мінімальну трирівневу архітектуру, REST API та ланцюжки простежуваності до майбутніх тестів. Ці артефакти є підґрунтям для програмної реалізації у ЛР2, тестування у ЛР3 та безпечного підключення AI-рекомендацій у ЛР4.
