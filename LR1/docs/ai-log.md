## 2. Призначення журналу

Журнал призначений для документування використання AI-асистента ChatGPT під час аналізу вимог, формування специфікації та перевірки проєктної документації Smart HelpDesk.

Основна мета застосування AI — критичне уточнення вимог, виявлення неоднозначностей, аналіз можливих суперечностей і перевірка узгодженості артефактів.

AI-асистент використовувався як допоміжний інструмент для аналізу та підготовки документації. Остаточні правила системи визначалися на основі методичних вказівок та формалізованих рішень замовника.

Записи AI-01–AI-03 відображають три задачі одного AI-сеансу від 18.11.2026. Запис AI-04 описує окремий етап підготовки матеріалів для публікації у GitHub від 19.11.2026.

Скорочені формулювання запитів передають зміст фактичних завдань, але не є дослівними повідомленнями користувача, якщо це окремо не зазначено.

## 3. Журнал взаємодії з AI

### AI-01. Аналіз та уточнення початкових вимог

**Дата:** 18.11.2026  
**Інструмент:** ChatGPT (GPT-6, текстовий режим)

**Мета:** проаналізувати початкові вимоги до Smart HelpDesk, визначити неоднозначності та уточнення, необхідні для формування перевірюваної специфікації.

**Скорочений зміст запиту:**

«Проаналізуй тему Smart HelpDesk відповідно до функціональних вимог FR-01–FR-08 та рішень замовника. Визнач неоднозначності й необхідні технічні уточнення, не додаючи функціональності поза встановленим обсягом».

**Отримані результати:**

- Проаналізовано функціональні вимоги FR-01–FR-08.
- Визначено основні сутності `Issue`, `Comment`, `User`.
- Уточнено використання технічної термінології для предметної області технічної підтримки.
- Виділено питання валідації та часткового оновлення.
- Визначено технічні рішення, які потребують додаткового погодження.

**Прийняті рішення:**

Збережено структуру обов'язкових вимог і використано технічні назви сутностей, сумісні з подальшою реалізацією REST API.

**Питання, що потребують погодження:**

- DEC-02 — правила обробки пробілів у коментарях.
- DEC-06 — передавання `assignee_id` під час створення звернення.
- DEC-07 — правила суворої перевірки типів даних.

**Перевірка результату:**

Результати аналізу зіставлено з розділами 2–3 методичних вказівок. Відокремлено задані факти замовника від технічних уточнень і припущень.

**Артефакт:** [requirements.md](requirements.md).

### AI-02. Формалізація вимог і розроблення контракту

**Дата:** 18.11.2026  
**Інструмент:** ChatGPT (GPT-6, текстовий режим)

**Мета:** сформувати перевірювану специфікацію, модель даних, правила переходів станів і REST API-контракт.

**Скорочений зміст запиту:**

«Підготуй сім User Stories із позитивними, негативними та граничними критеріями приймання, повну матрицю переходів статусів 3×3, правила PATCH і дев'ять REST API-маршрутів відповідно до методичних вимог».

**Отримані результати:**

- Сформовано сім User Stories для FR-01–FR-07.
- FR-08 виділено в окрему майбутню User Story для ЛР4.
- Визначено критерії приймання.
- Побудовано матрицю переходів між `OPEN`, `IN_PROGRESS`, `CLOSED`.
- Формалізовано правила часткового оновлення.
- Спроєктовано дев'ять REST API-маршрутів.
- Уточнено правила валідації та обробки помилок.

**Прийняті рішення:**

1. Відсутнє поле у PATCH не змінює збереженого значення.
2. `assignee_id: null` означає зняття призначення виконавця.
3. Порожній об'єкт `{}` відхиляється з HTTP 422.
4. Статус звернення змінюється лише окремою операцією.
5. Одночасна передача коректних і некоректних змін не повинна призводити до часткового оновлення даних.

**Перевірка результату:**

Проведено зіставлення всіх дев'яти комбінацій переходів статусів та перевірено узгодженість правил PATCH із REST API-контрактом і критеріями приймання.

**Артефакти:**

- [requirements.md](requirements.md)
- [api-contract.md](api-contract.md)

### AI-03. Перевірка узгодженості специфікації

**Дата:** 18.11.2026  
**Інструмент:** ChatGPT (GPT-6, текстовий режим)

**Мета:** перевірити внутрішню узгодженість специфікації, виявити потенційні суперечності й оцінити повноту простежуваності вимог.

**Скорочений зміст запиту:**

«Перевір зв'язки FR → US/AC → API → майбутній тест. Знайди можливі суперечності у використанні HTTP-кодів 404, 409, 422, правилах роботи із закритими зверненнями, коментарями та межах AI-функціональності».

**Отримані результати:**

- Перевірено відповідність функціональних вимог User Stories.
- Проаналізовано критерії приймання.
- Уточнено правила обробки HTTP-помилок.
- Перевірено матрицю переходів статусів.
- Перевірено правила роботи із закритими зверненнями.
- Проаналізовано зв'язки вимог із майбутніми тестами.

**Прийняті рішення:**

- HTTP 422 — некоректні вхідні дані.
- HTTP 404 — відсутній ресурс.
- HTTP 409 — операція суперечить поточному стану звернення.
- Додавання коментарів до закритих звернень залишається дозволеним.
- AI-функціональність FR-08 не реалізується в ЛР1.

**Функціональність, не включена до специфікації:**

- Реєстрація та автентифікація користувачів.
- Автоматична зміна пріоритету без підтвердження людини.
- Хмарні сповіщення.
- Додаткові функції, що виходять за межі вимог замовника.

Ці можливості розглядалися як приклади небажаного розширення обсягу, а не як фактичні пропозиції моделі, які обов'язково виникли під час взаємодії.

**Перевірка результату:**

Проведено статичне зіставлення вимог, API-контракту й матриці простежуваності.

Для структурної перевірки специфікації передбачено Python-скрипт `LR1/scripts/check_spec.py`.

**Артефакти:**

- [architecture.md](architecture.md)
- [traceability.csv](traceability.csv)
- [lab-01.md](lab-01.md)

## 4. Приклади критичної оцінки AI-результатів

Під час роботи з AI-асистентом результати аналізу перевірялися відповідно до вихідних рішень замовника.

**Заданий факт замовника:**

Під час створення звернення встановлюються `status=OPEN` та `priority=medium`, якщо інший пріоритет не вказано.

Передбачено двох фіксованих користувачів, а основні дані звернення після переходу до `CLOSED` не редагуються.

Ці правила визначено методичними вказівками, а не самостійно запропоновано AI.

**Корисне технічне уточнення:**

Для відтворюваного порядку списків звернень і коментарів запропоновано сортування за зростанням ідентифікатора (`id ASC`).

Це дозволяє забезпечити стабільний порядок навіть за однакових часових позначок створення.

**Припущення, що потребують погодження:**

- Обрізання крайніх пробілів у коментарях.
- Сувора типізація вхідних даних.
- Можливість передавання `assignee_id` під час створення звернення.

Ці уточнення задокументовано як DEC-02, DEC-06 та DEC-07.

**Недопустимі варіанти розширення функціональності:**

- Автоматичне змінення пріоритету звернення без підтвердження користувача.
- Запровадження автентифікації в межах ЛР1–ЛР3.
- Додавання хмарних сповіщень.

Зазначені можливості не включено до специфікації, оскільки вони виходять за межі обов'язкового обсягу.

Ці приклади наведено як контрольні альтернативи для перевірки відповідності специфікації, а не як дослівні відповіді AI.
