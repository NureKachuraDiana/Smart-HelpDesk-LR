**Документ:** LR1 / `docs/requirements.md`  
**Версія:** 1.0 (проєкт специфікації)  
**Дата:** 18.11.2026  
**Джерело вимог:** методичка «Штучний інтелект у програмній інженерії. Лабораторна робота 01: Вимоги та проєктування з AI-асистентом», розділи 2–3.  
**Тема:** «Розробка системи обліку та обробки звернень до технічної підтримки з використанням AI-асистента (Smart HelpDesk)».

> **Єдине джерело істини:** цей документ установлює модель даних, правила валідації, життєвий цикл звернення та правила PATCH. `architecture.md` і `api-contract.md` посилаються на нього. Створення робочого API та виклик LLM **не входять до ЛР1**.

## 1. Постановка задачі та межі

Підрозділу технічної підтримки невеликого програмного продукту потрібен локальний сервіс **Smart HelpDesk**. Користувач створює звернення (назва та опис проблеми), команда переглядає звернення, призначає одного з двох тестових агентів, визначає пріоритет, змінює статус і додає коментарі. Потрібно швидко отримувати відкриті звернення високого пріоритету за фільтрами. У ЛР4 планується необов'язкова AI-рекомендація категорії, пріоритету та короткого підсумку; жодна рекомендація не змінюватиме дані автоматично.

**Термінологія:** звернення = заявка = `issue` в технічних іменах, щоб зберегти контракт наступних лабораторних робіт. «Агент» означає фіксованого тестового користувача, а не автентифіковану особу.

**У межах ЛР2–ЛР3:** локальний REST API на Python/FastAPI, SQLite, автоматизовані сценарії pytest; без обов'язкового графічного інтерфейсу. У **ЛР1** готуються тільки узгоджені проєктні артефакти.

**Поза обсягом:** реєстрація та логін, паролі/OAuth/права доступу, листи та push-сповіщення, файли, видалення, повнотекстовий пошук, пагінація, Docker, хмарне розгортання, фронтенд і векторна база. Використовуються лише синтетичні дані; система не розрахована на публічне використання.

| FR-07 | Зберігати звернення й коментарі у SQLite між перезапусками; відхиляти неправильні дані й операції без часткового запису. | ЛР2–ЛР3 |

## 4. User stories та критерії приймання

Тести вказані у форматі **Given / When / Then**. Позначення AC — стабільні ідентифікатори для `traceability.csv`.

### US-01. Створення звернення (FR-01)
**Як** заявник, **я хочу** створити звернення з назвою й описом, **щоб** команда підтримки могла опрацювати проблему.

- **AC-01-01 (позитивний):** Given у БД немає звернень, When `POST /issues` із `{"title":"Не працює авторизація"}`, Then HTTP 201, відповідь має згенеровані `id`, `created_at`, `status=OPEN`, `priority=medium`, `description=""`, `assignee_id=null`.
- **AC-01-02 (межа):** Given коректна назва після `strip` має рівно 3 або 120 символів, When її надіслано, Then HTTP 201 і назва збережена без крайніх пробілів.
- **AC-01-03 (негативний):** Given назва після `strip` містить 2 символи, When викликається створення, Then HTTP 422, нового звернення немає.

### US-02. Перегляд і фільтрація (FR-02)
**Як** агент підтримки, **я хочу** переглядати та фільтрувати звернення, **щоб** знаходити термінові невирішені проблеми.

- **AC-02-01:** Given є `OPEN/high`, `OPEN/low`, `CLOSED/high`, When `GET /issues?status=OPEN&priority=high`, Then HTTP 200 і повернено тільки `OPEN/high`.
- **AC-02-02:** Given жодне звернення не відповідає фільтру, When запитано список, Then HTTP 200 та `[]`.
- **AC-02-03:** Given звернення з `id=999` відсутнє, When `GET /issues/999`, Then HTTP 404.

### US-03. Часткове редагування (FR-03)
**Як** агент підтримки, **я хочу** змінювати окремі поля звернення, **щоб** уточнювати проблему без втрати інших даних.

- **AC-03-01:** Given існує `OPEN` із `title=A...`, `priority=medium`, When `PATCH /issues/{id}` із `{"priority":"high"}`, Then HTTP 200, пріоритет змінено, а решта полів незмінні.
- **AC-03-02:** Given є коректна зміна `title` і некоректна `priority="urgent"`, When надіслано їх разом, Then HTTP 422 і **обидва** початкові значення залишились.
- **AC-03-03:** Given заявка `CLOSED`, When надіслано валідне редагування, Then HTTP 409, звернення не змінене.

### US-04. Життєвий цикл (FR-04)
**Як** агент підтримки, **я хочу** керувати статусом звернення, **щоб** бачити поточну стадію його опрацювання.

- **AC-04-01:** Given `OPEN`, When `PATCH /issues/{id}/status` із `{"status":"IN_PROGRESS"}`, Then HTTP 200, статус `IN_PROGRESS`.
- **AC-04-02:** Given `CLOSED`, When надіслано `{"status":"OPEN"}`, Then HTTP 409, статус лишається `CLOSED`.
- **AC-04-03:** Given `OPEN`, When повторно встановлено `OPEN`, Then HTTP 200 без зміни запису.

### US-05. Призначення агента (FR-05)
**Як** координатор підтримки, **я хочу** призначати або знімати агента, **щоб** керувати відповідальністю за звернення.

- **AC-05-01:** Given `OPEN` без призначення, When `PATCH` із `{"assignee_id":1}`, Then HTTP 200 і призначено `Agent A` (`id=1`).
- **AC-05-02:** Given призначено `2`, When `PATCH` із `{"assignee_id":null}`, Then HTTP 200 та `assignee_id=null`.
- **AC-05-03:** Given `OPEN`, When `PATCH` із `{"assignee_id":3}`, Then HTTP 422, попередній виконавець збережений.

### US-06. Коментарі (FR-06)
**Як** агент підтримки, **я хочу** додавати та читати коментарі, **щоб** зберігати історію обговорення проблеми.

- **AC-06-01:** Given заявка `CLOSED` існує, When `POST /issues/{id}/comments` із `{"author_id":1,"body":"Проблему підтверджено"}`, Then HTTP 201, коментар має автора, час, `issue_id`.
- **AC-06-02:** Given `body` складається лише з пробілів, When надіслано коментар, Then HTTP 422, коментар не записаний.
- **AC-06-03:** Given є два коментарі, When `GET /issues/{id}/comments`, Then HTTP 200, обидва повернуті у порядку створення.

### US-07. Стійкість збереження і валідації (FR-07)
**Як** учасник команди, **я хочу** зберігати звернення між запусками й отримувати зрозумілі помилки, **щоб** не втрачати виконану роботу.

- **AC-07-01:** Given створено звернення й коментар, When застосунок перезапущено з тією самою SQLite БД, Then обидва записи доступні за GET.
- **AC-07-02:** Given звернення існує, When PATCH має `{"description":null}`, Then HTTP 422, попередній опис збережений.
- **AC-07-03:** Given неіснуюча заявка 999, When запитано додати коментар, Then HTTP 404 і нових коментарів немає.

### US-08. Майбутня AI-підказка (FR-08, лише ЛР4)
**Як** агент підтримки, **я хочу** отримати рекомендовану категорію, пріоритет і короткий підсумок, **щоб** швидше класифікувати звернення. **У ЛР1–ЛР3 не розробляти**; детальний API та критерії визначити під час ЛР4. Будь-яка пропозиція потребуватиме рішення людини та не змінюватиме заявку автоматично.

## 5. Формальний контракт даних

### 5.1. Сутність `Issue` (звернення)

| Поле : тип | Встановлює | POST | Значення за замовчуванням / null | Перевірка, нормалізація, PATCH |
|---|---|---|---|---|
| `id: int` | Сервер | Заборонено в тілі | Немає; NOT NULL | Додатний унікальний авто-ID, лише читання. |
| `title: str` | Клієнт | **Обов'язково** | null заборонено | `strip` з країв, 3–120 символів **після strip**; редагується, поки не CLOSED. |
| `description: str` | Клієнт | Необов'язково | `""`; null заборонено | 0–2000 символів, зберігається дослівно, без `strip`; редагується, поки не CLOSED. |
| `status: enum` | Сервер; окрема операція | Заборонено в тілі | `OPEN`; null заборонено | `OPEN`, `IN_PROGRESS`, `CLOSED` (чутливі до регістру); зміна тільки окремим API. |
| `priority: enum` | Клієнт | Необов'язково | `medium`; null заборонено | `low`, `medium`, `high` (чутливі до регістру); редагується, поки не CLOSED. |
| `assignee_id: int \| null` | Клієнт | Необов'язково | `null` | Тільки `1`, `2`, `null`; у PATCH null = зняти призначення; після CLOSED не змінюється. |
| `created_at: UTC datetime` | Сервер | Заборонено в тілі | Поточний час UTC; NOT NULL | ISO 8601 з `Z`; незмінний. |

### 5.2. Сутність `User` (фіксований довідник)

| Поле : тип | Джерело / правила |
|---|---|
| `id: int` | Статично: `1`, `2`; унікальний додатний; не створюється через API. |
| `name: str` | Статично: `Agent A` для id=1, `Agent B` для id=2. |

`User` потрібен **тільки** для `assignee_id` та `author_id`; він не є доказом особи. Не додавати автентифікацію.

### 5.3. Сутність `Comment`

| Поле : тип | Встановлює | POST | Правила |
|---|---|---|---|
| `id: int` | Сервер | Заборонено | Унікальний додатний авто-ID, незмінний. |
| `issue_id: int` | Сервер із path | Заборонено в тілі | Посилається на існуючий `Issue.id`, NOT NULL. |
| `author_id: int` | Клієнт | **Обов'язково** | Тільки `1` або `2`, null заборонено. |
| `body: str` | Клієнт | **Обов'язково** | `strip` з країв, 1–1000 символів **після strip**; null, порожній/пробільний текст заборонені. |
| `created_at: UTC datetime` | Сервер | Заборонено | Поточний час UTC, ISO 8601 `Z`, незмінний. |

**Спільні правила:** JSON-тіло повинно бути об'єктом; неописані поля заборонені (422). Boolean не можна підміняти ідентифікатором-int; числові рядки не приводяться неявно до чисел. `id` у path — додатне ціле: некоректний тип / `id ≤ 0` → 422, коректний, але відсутній id → 404. Лише `assignee_id` допускає JSON `null`. Усі дати створення визначає сервер, їх не можна задавати або редагувати клієнту. Вихідні назви полів і регістр значень точні.

### 5.4. Матриця переходів статусів (усі 9 комбінацій)

| Поточний статус \ Запитаний статус | `OPEN` | `IN_PROGRESS` | `CLOSED` |
|---|---|---|---|
| **OPEN** | Ідемпотентно, 200 | Дозволено, 200 | Дозволено, 200 |
| **IN_PROGRESS** | Заборонено, 409 | Ідемпотентно, 200 | Дозволено, 200 |
| **CLOSED** | Заборонено, 409 | Заборонено, 409 | Ідемпотентно, 200 |

Під час ідемпотентного виклику дані й `created_at` не змінюються. Заборонений перехід — HTTP 409; збережений стан незмінний.

| Операція для `CLOSED` | Дозволено? |
|---|---|
| Читати звернення та фільтрувати | Так |
| Редагувати `title`, `description`, `priority`, `assignee_id` | **Ні**, 409 |
| Повторно встановити `CLOSED` | Так, 200 без зміни |
| Перевести до `OPEN` або `IN_PROGRESS` | **Ні**, 409 |
| Додавати та читати коментарі | Так |

### 5.5. Єдиний контракт `PATCH /issues/{id}`

1. **Поле відсутнє** → збережене значення залишається без змін; **поле передано** → проходить валідацію і потім оновлюється.
2. `{"assignee_id": null}` → зняти призначення. `null` для `title`, `description`, `priority`, `status`, `author_id`, `body` не допускається (422).
3. **Порожнє тіло `{}`** → 422: немає змін для внесення.
4. **Зайве/невідоме поле**, `status`, `id` або `created_at` у PATCH → 422; змінювати статус можна лише через `/status`.
5. **Змішані коректні й некоректні поля** → 422 та **повний відкат**, жодне поле не змінюється.
6. **Валідне редагування CLOSED** → 409, нічого не змінюється. **Валідний PATCH без фактичної різниці** у OPEN/IN_PROGRESS → 200 з незмінними даними.
7. **Атомарність:** уся перевірка даних проводиться **перед** транзакцією оновлення; зміни фіксуються лише після успішної валідації всього запиту.
8. Порядок визначення помилок: (а) валідність path/query/body → **422**, (б) наявність звернення → **404**, (в) допустимість операції в його стані → **409**, (г) виконання → **200/201**. Також діє для запитів зі зміною статусу та коментарями.

### 5.6. Зв'язки, порядок та сховище

`Issue.assignee_id` — nullable FK на `User.id`; `Comment.author_id` — обов'язковий FK на `User.id`; `Comment.issue_id` — обов'язковий FK на `Issue.id`. У SQLite необхідно ввімкнути `PRAGMA foreign_keys=ON`, а користувачів 1 і 2 створити як тестові записи під час ініціалізації БД. Усі операції запису проводяться транзакційно.

Списки `Issue` та `Comment` упорядковані за зростанням `id` (порядок створення, навіть за однакових `created_at`). Фільтри `status` і `priority` застосовуються як **AND**. Немає збігів → HTTP 200 і порожній масив `[]`.

### 5.7. Каталог результатів і помилок

| Ситуація | Результат / HTTP |
|---|---|
| Успішне створення звернення або коментаря | 201 + повний створений об'єкт |
| Успішне читання, змінення, включно з повторним статусом | 200 + об'єкт або масив |
| Неіснуючий позитивний `issue_id` | 404, `NOT_FOUND` |
| Необов'язковий фільтр не має збігів | 200 + `[]` |
| Некоректні типи, межі, enum, невідомі поля, `null`, `{}`, некоректний path | 422, `VALIDATION_ERROR` |
| Перехід статусу не за матрицею | 409, `INVALID_STATE_TRANSITION` |
| Валідне редагування CLOSED | 409, `ISSUE_CLOSED` |

Стандартний формат помилки: `{"error":{"code":"...","message":"...","details":[]}}`. Поле `details` — масив структурованих пояснень (`field`, `reason`) і може бути порожнім; не включати внутрішні трасування стека у відповідь.

## 6. Аналіз неоднозначностей та журнал рішень

**Питання з початкового неповного запиту:** як визначати пріоритет за відсутності вибору; що робити при повторному статусі; чи дозволено відкрити CLOSED; чи можна коментувати CLOSED; чи можна зняти призначення; чи має AI змінювати звернення. Відповіді для всіх шести містяться в рішеннях замовника; це **задані факти**, а не самостійні припущення.

| ID | Питання / рішення | Класифікація та обґрунтування |
|---|---|---|
| DEC-01 | `title` обрізати по краях і вимірювати **після** обрізання; `description` зберігати без додаткового `strip`. | Перша частина — **заданий факт**; друга — **технічне уточнення**, щоб не губити формат повідомлення. |
| DEC-02 | Коментар з одних пробілів не вважати непорожнім; `body` обрізати по краях перед перевіркою 1–1000. | **Припущення-уточнення для погодження**, узгоджується з вимогою «непорожній текст». |
| DEC-03 | Невалідний запит = 422, відсутній ресурс = 404, заборонений стан = 409; порядок перевірки 422→404→409. | **Технічна домовленість команди**, щоб API і тести не суперечили одне одному. |
| DEC-04 | Для відтворюваного порядку «за створенням» використовувати `id ASC`, а не тільки `created_at`. | **Технічне уточнення**, виключає нічиї при однаковій часовій позначці. |
| DEC-05 | У FR-08 лише спроєктувати точку інтеграції; не вводити endpoint AI чи мережеві виклики раніше ЛР4. | **Задана межа обсягу**, забороняє приховане розширення функціональності. |
| DEC-06 | `POST /issues` може приймати необов'язковий `assignee_id`; решта дозволених полів — тільки `title`, `description`, `priority`. | **Уточнення контракту для погодження**: не змінює кількості операцій і підтримує вимогу призначення. |
| DEC-07 | Неявні приведення типів (`"1"` до `1`) і надлишкові JSON-поля відхиляти. | **Уточнення для погодження** з метою однозначної перевірки API. |

**Потрібно підтвердити перед ЛР2:** DEC-02, DEC-06, DEC-07 (і за потреби DEC-03/04), якщо викладач очікує іншу політику. Без погодження **не змінювати** жодного з рішень замовника з методички. AI-пропозиція додати авторизацію або автоматичний пріоритет суперечила б обсягу й не входить до специфікації; така пропозиція тут наведена як контрольна альтернатива, а **не** як нібито фактична відповідь моделі.
