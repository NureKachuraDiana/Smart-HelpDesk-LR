# Звіт до лабораторної роботи №1

**Дисципліна:** Штучний інтелект у програмній інженерії  
**Тема:** «Розробка системи обліку та обробки звернень до технічної підтримки з використанням AI-асистента (Smart HelpDesk)»  
**Назва ЛР1:** «Вимоги та проєктування з AI-асистентом: від неструктурованого запиту до перевірюваної специфікації»  
**Студентки:** Качура Діана та Ситник Поліна
**Група:** ПЗПІ-23-6  
**Дата виконання:** 18–19 листопада 2026 року  

## 1. Мета роботи

Навчитися використовувати AI-асистента для критичного аналізу й уточнення вимог, перетворення неструктурованого запиту замовника на перевірювану специфікацію та проєктування мінімальної архітектури й REST API системи Smart HelpDesk.

Основною метою лабораторної роботи №1 є формування узгодженої специфікації, а не реалізація працюючого програмного застосунку. Програмна реалізація передбачена в ЛР2, тестування — у ЛР3, а інтеграція AI-рекомендацій — у ЛР4.

## 2. Виконана робота

Вихідний приклад Mini Issue Tracker адаптовано до предметної області обліку та обробки звернень до технічної підтримки без розширення обов'язкового функціонального обсягу.

У процесі виконання лабораторної роботи:

1. Проаналізовано вихідні вимоги замовника та визначено неоднозначності постановки задачі.
2. Сформовано функціональні вимоги FR-01–FR-07 та майбутню FR-08 для AI-рекомендацій.
3. Визначено шість перевірюваних нефункціональних вимог (NFR).
4. Розроблено сім User Stories для поточного обсягу та одну відкладену User Story для ЛР4.
5. Сформульовано позитивні, негативні та граничні критерії приймання.
6. Визначено сутності `Issue`, `User`, `Comment`, їхні атрибути та зв'язки.
7. Побудовано повну матрицю з дев'яти можливих переходів між статусами `OPEN`, `IN_PROGRESS`, `CLOSED`.
8. Формалізовано правила валідації, часткового оновлення (PATCH) та атомарності операцій.
9. Спроєктовано трикомпонентну архітектуру, модель сутностей і дев'ять маршрутів REST API.
10. Підготовлено два архітектурні рішення (ADR) та матрицю простежуваності вимог до майбутніх тестів.
11. Проведено аналіз документації з використанням ChatGPT, автоматизовану перевірку специфікації та перехресне рев'ю.

Основні проєктні документи збережено в каталозі `LR1/docs/` GitHub-репозиторію.

## 3. Ключові рішення та уточнення

**Рішення 1 — дотримання вихідних правил замовника.**

Під час створення звернення система встановлює початковий статус `OPEN` і типовий пріоритет `medium`. Передбачено двох фіксованих тестових виконавців.

Після переходу звернення до статусу `CLOSED` повернення до попередніх станів і редагування основних полів заборонені, проте перегляд та додавання коментарів залишаються доступними.

Ці правила встановлено методичними вказівками, тому їх не розглянуто як самостійні припущення AI.

**Рішення 2 — забезпечення атомарного часткового оновлення (PATCH).**

У контракті визначено відмінності між основними випадками:

- Відсутнє поле — його збережене значення не змінюється.
- `assignee_id: null` — знімається призначення виконавця.
- Порожній об'єкт `{}` — повертається HTTP 422.
- Одночасне передавання коректних і некоректних змін — увесь запит відхиляється без зміни даних.

Правила перевіряються за критерієм AC-03-02 та запланованим тестом `test_patch_atomic_failure_and_closed`.

**Рішення 3 — контрольована інтеграція штучного інтелекту.**

Функціональність AI-рекомендацій (FR-08) відкладено до ЛР4. Передбачено, що AI-компонент рекомендуватиме категорію, пріоритет і короткий підсумок звернення, але не змінюватиме його автоматично.

Основні функції Smart HelpDesk повинні залишатися доступними навіть за відсутності підключення до LLM.

## 4. Використання AI та перевірка результату

Для аналізу вимог, уточнення неоднозначностей і перевірки специфікації використано ChatGPT (GPT-6) у текстовому режимі.

AI-асистент застосовувався для визначення технічних уточнень, перевірки узгодженості User Stories, моделі даних, правил валідації, REST API-контракту та матриці простежуваності.

**Показовий випадок 1 — перевірка правил PATCH.**

Під час аналізу уточнено різницю між відсутнім полем, значенням `null` та порожнім об'єктом запиту. Результат перевірено шляхом зіставлення формалізованих бізнес-правил із REST API-контрактом і критеріями приймання.

**Показовий випадок 2 — перевірка меж застосування AI.**

Під час проєктування перевірено, що функціональність FR-08 належить лише ЛР4. Тому в межах ЛР1 не передбачено окремого AI-endpoint або автоматичної зміни звернень за рекомендацією моделі.

Додатково перевірено відповідність кодів HTTP:

- `404` — запитуваний ресурс не знайдено.
- `409` — операція суперечить поточному стану звернення.
- `422` — некоректні вхідні дані.

Результати взаємодії з AI, прийняті рішення та способи їх перевірки зафіксовано в [журналі використання AI](ai-log.md).

Технічні уточнення DEC-02, DEC-06 та DEC-07 позначено як рішення, що потребують погодження перед остаточною реалізацією, оскільки вихідні правила замовника не визначають усі їхні деталі.

## 5. Результати перевірки та простежуваності

Для кожної з семи поточних функціональних вимог FR-01–FR-07 підготовлено щонайменше одну User Story, позитивний та негативний або граничний критерії приймання, відповідний REST API-маршрут і майбутній тест.

**Покриття специфікації:**

7 / 7 × 100% = **100%**.

Вимогу FR-08 не включено до розрахунку, оскільки її реалізація передбачена в ЛР4. Отриманий показник характеризує повноту простежуваності вимог, а не покриття програмного коду автоматизованими тестами.

Матрицю простежуваності наведено у файлі [traceability.csv](traceability.csv).

Проведено аналіз узгодженості документації за допомогою ChatGPT та автоматизовану перевірку наявності функціональних вимог, User Stories, критеріїв приймання, REST API-маршрутів і зв'язків простежуваності.

Для автоматизації перевірки використано Python-скрипт `LR1/scripts/check_spec.py` та GitHub Actions.

**Перехресне рев'ю проєктної документації проведено студенткою Ситник Поліною 19.11.2026.**

Під час рев'ю перевірено функціональні та нефункціональні вимоги, User Stories, критерії приймання, модель даних, бізнес-правила, архітектуру системи, REST API-контракт і матрицю простежуваності.

За зафіксованими результатами перевірки зауважень не виявлено, додаткові виправлення не знадобилися.

Результати перевірки задокументовано у файлі [peer-review.md](peer-review.md).

Реалізація програмного застосунку, запуск REST API та інтеграційне тестування не входять до обсягу лабораторної роботи №1.

## 6. Висновки

У ході лабораторної роботи №1 сформовано перевірювану специфікацію системи Smart HelpDesk для обліку й обробки звернень до технічної підтримки.

Визначено функціональні та нефункціональні вимоги, сформовано User Stories, критерії приймання, модель даних, правила валідації, матрицю переходів статусів, контракт часткового оновлення, архітектуру системи та REST API.

Проведено аналіз із використанням AI-асистента, автоматизовану перевірку документації та перехресне рев'ю. Сформована матриця простежуваності забезпечує покриття всіх семи функціональних вимог поточного обсягу.

Отримані результати створюють основу для програмної реалізації системи у ЛР2, автоматизованого тестування у ЛР3 та інтеграції AI-рекомендацій у ЛР4.
